# Overseer v1.1 operations

Overseer v1.1 is a source-ready, always-running local operations runtime. The
`overseer.service` process owns a bounded scheduler and writes durable job,
lease, run, incident, repair, and heartbeat state to the configured SQLite
store. The API and dashboard read those projections. They do not run probes or
other collectors inline.

This repository contains only a source-controlled user-service template. Task
9 does not install, copy, enable, start, restart, migrate, or otherwise change
any live service. Activation is a separate approval-gated operation described
below.

## Service template and runtime environment

The template at `systemd/overseer.service` expects this user-owned file:

```text
%h/.config/overseer/runtime.env
```

It must define these three absolute paths:

```dotenv
OVERSEER_PYTHON=/absolute/path/to/python
OVERSEER_INSTALL=/absolute/path/to/Overseer
OVERSEER_STORE=/absolute/path/to/overseer.sqlite3
```

`OVERSEER_PYTHON` is the interpreter with Overseer's dependencies installed.
`OVERSEER_INSTALL` is the checkout or installed source tree containing `src/`.
`OVERSEER_STORE` is the primary SQLite file; its parent directory must already
exist and be writable by the service user. Do not put tokens, passwords, API
keys, peer secrets, or other credentials in this environment file.

Create the file and its parent directory with user-only permissions:

```bash
install -d -m 0700 "$HOME/.config/overseer"
install -m 0600 /path/to/reviewed/runtime.env "$HOME/.config/overseer/runtime.env"
```

The source unit uses no hard-coded checkout, interpreter, or store path. It has
no socket unit, `ListenStream`, or network listener. Outbound read-only probes
remain governed by the stored target contracts; this unit does not publish an
API. The API remains a separately owned loopback service and protected-gateway
route.

## Job model and status commands

Job definitions are stable IDs with an independent interval, deterministic
jitter, timeout, priority, concurrency key, retention limit, repair policy,
backoff cap, and circuit threshold. The seeded job kinds are:

| Kind | Default interval | Default timeout | Purpose |
| --- | ---: | ---: | --- |
| `health_probe` | target value, otherwise 120 seconds | target value, otherwise 30 seconds | Read-only HTTP, HTTPS, MCP, process, command, log, or manual health evidence |
| `host_inspection` | 300 seconds | 1 second | Bounded host and listener observations |
| `physical_discovery` | 900 seconds | 5 seconds | Physical and storage identity observations |
| `virtual_discovery` | 300 seconds | 5 seconds | Virtual listener and asset observations |
| `crew_dispatch` | 120 seconds | 5 seconds | Persisted Sisko-owned message dispatch work |
| `usage_continuation` | 120 seconds | 5 seconds | Persisted Quark continuation dispatch work |
| `knowledge_capture` | 300 seconds | 5 seconds | Bounded Ezri capture of selected local records |
| `station_audit` | 600 seconds | 5 seconds | Bounded cross-domain station audit |
| `package_inspection` | 1800 seconds | 5 seconds | Read-only package/update observation |
| `freshness_projection` | 60 seconds | 5 seconds | Observe externally owned timer/service freshness |

Health-target fields remain compatible with v1.0. Missing schedule fields keep
the 120-second interval, zero jitter, 30-second timeout, and `triage_only`
repair policy. Fixed jobs use their kind defaults above. The scheduler is
bounded to two workers globally and one active run per concurrency key; a
slow collector therefore cannot create an unbounded worker or request fanout.

Read-only JSON status commands use an explicit store:

```bash
PYTHONPATH="$OVERSEER_INSTALL/src" "$OVERSEER_PYTHON" -m overseer.cli runtime-status --store "$OVERSEER_STORE"
PYTHONPATH="$OVERSEER_INSTALL/src" "$OVERSEER_PYTHON" -m overseer.cli collection-jobs --store "$OVERSEER_STORE"
PYTHONPATH="$OVERSEER_INSTALL/src" "$OVERSEER_PYTHON" -m overseer.cli collection-scheduler-status --store "$OVERSEER_STORE"
PYTHONPATH="$OVERSEER_INSTALL/src" "$OVERSEER_PYTHON" -m overseer.cli collection-runs --store "$OVERSEER_STORE" --limit 50
PYTHONPATH="$OVERSEER_INSTALL/src" "$OVERSEER_PYTHON" -m overseer.cli collection-incidents --store "$OVERSEER_STORE" --status open
```

`seed-collection-jobs` is the idempotent local migration/seed command. It may
write only the Overseer store. The `run` command in the unit performs a normal
continuous scheduler loop; `--once` is reserved for a disposable canary or a
controlled diagnostic. The old collector flags remain accepted as deprecated
family selectors for one compatibility release. They do not mean “run every
collector on every tick” and are deliberately absent from the service unit.

## Requests, coalescing, and failure state

The API `POST /collections/jobs/{job_id}/run` and CLI
`request-collection-run` create a durable request. A repeated pending request
for the same job is coalesced, and the response reports its request ID,
`queued`/`coalesced` status, earliest execution time, and circuit state. The
request path never calls the adapter, waits for a probe, or returns probe
evidence. This keeps dashboard refreshes GET-only and prevents a user or
browser retry from swamping the host.

Successful runs schedule the next interval plus stable per-job jitter. Failed
and timed-out runs use capped exponential backoff. Once a job reaches its
configured failure threshold, its circuit becomes `open` until cooldown; the
next allowed attempt is half-open and a successful verification closes it.
Leases fence stale workers and preserve the concurrency limits across restart.
Runs and evidence are retained within their configured bounds.

An unsuccessful run opens or advances a durable triage incident. Incidents
retain owner, failure category, bounded evidence IDs, generation, repair state,
and resolution. A repair attempt is idempotent and must be verified by a later
collection run before incident closure.

The only automatic repairs are exact, preapproved low-risk runbooks for jobs
whose policy is `preapproved_low_risk`, such as a bounded read-only retry or
bounded evidence pruning. A `triage_only` job records the incident and waits
for an operator/owner. A service restart, package change, permission or
identity change, device/VM/container action, route/listener/firewall/gateway
change, IDS action, or external-project action produces an
`approval_required` plan and does not execute automatically. Approval, claim,
IDS review, adapter enablement, audit, rollback, and verification remain
separate gates.

## Psychlo and Quark timer ownership

Psychlo accounting and Quark scheduling remain owned by their existing
dedicated service/timer pairs. Overseer seeds freshness-projection jobs for
their timer/service state; it does not create a duplicate timer, invoke their
accounting protocol inline, alter their credentials, or replace their stores.
An approved local reconciliation request must have its own idempotency key and
must preserve the signed peer and usage-attribution contracts.

## Source migration and disposable-store canary

The safe migration sequence is:

1. Review the source unit, current store schema, current service command, and
   `git diff` from the approved v1.1 base. Preserve the existing live unit,
   store, journals, and rollback copy.
2. Run migrations and `seed-collection-jobs` against a disposable copy of the
   store. Confirm stable job IDs, no duplicate Psychlo/Quark timer jobs,
   schema/index repair, and expected status JSON.
3. Run a disposable-store canary with `run --once` and the scheduler-backed
   adapters. Confirm bounded workers, lease release, durable run/heartbeat
   state, failure backoff/circuit behavior, incident/repair disposition, and
   that queue requests do not execute inline.
4. Prepare an exact admin change plan naming the reviewed source commit/tree,
   unit hash, environment-file path, interpreter, install path, store path,
   migration command, seed command, enable/start or restart commands, health
   checks, journal checks, rollback commands, and responsible approver.
5. Obtain the required human approval plus any IDS, claim, adapter-enablement,
   and external-owner approvals. This task provides no approval and performs
   no activation.
6. During the separately approved change window, install/update the unit,
   migrate/seed the live store, and activate the service under the exact plan.
   Verify heartbeat freshness, scheduler status, job/run/incident projections,
   API authentication and prefix routing, bounded request latency, and that
   the existing Psychlo/Quark timers remain independently healthy.

Rollback is an exact approved plan: stop or disable the v1.1 unit only as
authorized, restore the prior reviewed unit/command and compatible store
backup or migration path, verify the old runtime heartbeat/API integration,
and preserve all v1.1 SQLite files, WAL/journal files, logs, request/run/
incident/repair records, migration output, hashes, and approval/audit records
for forensic comparison. Never delete or rewrite evidence to make a rollback
look clean.

## Compatibility and non-mutation boundary

V1.1 preserves existing resource/target IDs, owner domains, API authentication,
`/Overseer` gateway-prefix compatibility, health probe transports, provider
identities, Psychlo signatures, Quark continuation semantics, Roadex authority,
and existing approval/audit/secret boundaries. The new scheduler augments
health-target metadata; it does not rename or replace integrations.

Overseer may read or stage state for other projects and services. It may not
modify their source, configuration, database, service, credentials, network
policy, firewall, gateway, provider session, or timer. Any such action remains
an explicitly approved, separately executed integration workflow.
