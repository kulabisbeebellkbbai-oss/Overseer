# Overseer v1.1.6 dedicated-principal activation plan

Approval status: architecture approved; live activation not approved.

Work type: high-risk local account, ownership, system-service, credential, and
authority-store migration.

Hardware requirement: none. An authenticated local administrator must be
present for the activation and rollback checkpoints.

This is the exact shape of the later activation. Release commit/tree/digests,
backup paths, generated credential paths, and the migration timestamp remain
unresolved until the source branch is final. Do not run this plan while any
placeholder remains or before the user approves the rendered command set.

## Change boundary

The activation may create only:

- system user/group `overseer` with no login shell;
- root-owned release `/opt/overseer/releases/<commit>-<manifest-digest>`;
- protected state `/var/lib/overseer` and root executor state
  `/var/lib/overseer-executor`;
- configuration `/etc/overseer`;
- system units `overseer-api.service`, `overseer-runtime.service`,
  `overseer-admin-executor.socket`, `overseer-admin-executor@.service`, and the
  disposable `overseer-approval-smoke.service`;
- one user-readable compatibility copy of the ordinary API client token at the
  existing path. This is not a human approval secret.

It may not change gateway, firewall, route, VPN, SSH, other-project source,
other-project services, Codex login files, tmux state, or any non-Overseer
database.

Stop if the account already exists with different attributes, a system unit
name is already owned by another package, the live API is unhealthy, the
reviewed tree is dirty, the old database is not owner-only, WAL backup cannot
be obtained, the gateway owner has an unreviewed route change, or any required
user bridge remains incomplete. Also stop unless both rollback units are bound
to the preserved v1.1.5 release and their unit, drop-in, runtime-environment,
interpreter, and release-manifest hashes have been captured in the activation
package. The v1.1.6 checkout must never be substituted into those user units.

## Prepared artifacts

The final activation package must contain hashes for:

- every release file and dependency copied into the immutable release;
- all rendered units and the exact root executor allowlist;
- the copied Psychlo binding snapshot;
- the old database, its WAL-consistent backup, and the migrated database;
- both verifier documents, the executor public key, and credential metadata
  without secret values;
- the ordinary API token equality check between the root-managed service
  credential source and the existing user-readable client copy.

Admin and Roadex approval secrets are entered interactively during verifier
creation, are confirmed once, and are never written, printed, logged, placed in
an environment variable, or reused. The documents contain only salts and
digests. The two secrets must be different from each other and from the API
token.

Generate the two staged verifier documents with
`python3 -m overseer.cli create-approval-verifier` and their exact scopes. Each
secret is at least 20 UTF-8 bytes with no whitespace or control characters.
The former plaintext human-approval file is neither copied nor parsed by
v1.1.6; it remains only inside the preserved rollback boundary.

## Rendered activation commands

The final plan will replace every angle-bracket value with an absolute,
validated value and will use `install`, never an unresolved glob or recursive
copy.

```bash

sudo install -d -o root -g root -m 0755 /opt/overseer /opt/overseer/releases
sudo install -d -o root -g root -m 0555 '/opt/overseer/releases/<commit>-<manifest-digest>'
sudo install -d -o overseer -g overseer -m 0700 /var/lib/overseer
sudo install -d -o root -g root -m 0700 /var/lib/overseer-executor
sudo install -d -o root -g overseer -m 0750 /etc/overseer

sudo install -o root -g root -m 0444 '<staged-release-manifest>' '/opt/overseer/releases/<commit>-<manifest-digest>/release-manifest.json'
sudo install -o root -g root -m 0555 '<staged-python>' '/opt/overseer/releases/<commit>-<manifest-digest>/venv/bin/python'
# The final rendered plan lists one install command per reviewed release file.

sudo install -o overseer -g overseer -m 0600 '<admin-verifier>' /etc/overseer/admin-approval-verifier.json
sudo install -o overseer -g overseer -m 0600 '<roadex-verifier>' /etc/overseer/roadex-fixture-approval-verifier.json
sudo install -o root -g root -m 0600 '<api-token-source>' /etc/overseer/api-token
```

The primary database is copied only from a quiesced, WAL-consistent backup.
Historical approval and execution rows are retained for evidence but marked
non-executable by the migration. The final migration command is a reviewed
Overseer subcommand bound to the source and destination digests; it is not a
raw `cp` of a live SQLite file.

## Staged start and acceptance

After artifact verification and a separate approval of the rendered plan:

1. daemon-reload and start the executor socket only;
2. start the system runtime/API against a disposable migrated copy on a
   temporary loopback port;
3. verify scheduler heartbeats, projection-only UI refresh, Psychlo/Roadex
   protocol health, API authorization, separate verifier scopes, signed-ticket
   rejection controls, and zero live executor commands;
4. stop the disposable canary;
5. quiesce the two old user units, take the final migration backup, bind the
   system API to `127.0.0.1:8766`, and start runtime/API;
6. verify direct API health, protected-gateway health, UI desktop/tablet/mobile
   behavior, scheduler leases, and integration status;
7. run the approval smoke: ordinary API token is forbidden, the admin verifier
   approves the exact digest, the root executor restarts only
   `overseer-approval-smoke.service`, and replay returns the stored receipt
   without a second command;
8. keep all non-smoke executor operations disabled.

Positive and negative controls are mandatory: wrong scope, wrong secret,
ordinary API token, modified ticket, expired ticket, reused nonce, unlisted
unit, direct user-service command, and executor crash-after-claim must all fail
closed.

## Rollback

Rollback is triggered by API/gateway failure, missing scheduler heartbeats,
database mismatch, integration regression, unauthorized acceptance, executor
replay, or any ownership/mode drift.

```bash
sudo systemctl stop overseer-api.service overseer-runtime.service overseer-admin-executor.socket
sudo systemctl disable overseer-api.service overseer-runtime.service overseer-admin-executor.socket
sudo systemctl daemon-reload
test "$(grep '^OVERSEER_INSTALL=' /home/god/.config/overseer/runtime.env)" = \
  'OVERSEER_INSTALL=/home/god/.local/share/overseer/releases/v1.1.5-5196757'
test -d /home/god/.local/share/overseer/releases/v1.1.5-5196757
# Verify the captured v1.1.5 unit, drop-in, runtime-env, interpreter, and release hashes here.
systemctl --user start overseer.service overseer-api.service
curl --fail --silent --show-error http://127.0.0.1:8766/health
```

Rollback restores the prior user units and their untouched original database;
it does not copy the migrated system database back over the old authority.
System-state, config, release, and executor artifacts remain inert and retained
for audited cleanup. Deleting the account, release, database, keys, or evidence
requires a separate exact cleanup approval.
