# Overseer v1.1.6 dedicated-principal activation plan

Approval status: architecture approved; live activation not approved.

Work type: high-risk local account, ownership, system-service, credential, and
authority-store migration.

Hardware requirement: none. An authenticated local administrator must be
present for the activation and rollback checkpoints.

## Preparation package implementation

The source implementation in `overseer.activation_package` prepares this plan
without executing it. `stage-sqlite-runtime` first creates the owner-only
package and copies only the independently digest-approved SQLite binary to
`private/runtime-input/libsqlite3.so.0`. `prepare-package` then accepts only
that package-bound inode plus paths and numeric account identifiers. It
inventories the clean Git source, release-local dependencies, resolved
interpreter, complete standard library, approved release-local SQLite runtime,
rendered units, credentials, and rollback inputs, and performs a bounded online
SQLite backup rehearsal. It migrates only a second copied canary and stops with
status `awaiting_human_verifiers`.

Preparation also requires the separately reviewed source commit and tree as
exact inputs. The tree is derived from the captured commit object, never from a
second independent `HEAD` resolution, and both values must match those approved
inputs before any source blob is inventoried. Git replace objects are disabled,
and all tracked source plus activation-control bytes are read from their bound
Git objects rather than from mutable working-tree paths.

The package's `activation-contract.json` stores exact argv arrays and always
sets `liveExecutionApproved` to `false`. It is evidence for a later approval;
it is not an executable shell script and preparing or sealing it grants no
activation authority. The contract uses the exact `god` user-manager runtime
path when stopping or restoring the v1.1.5 user units, so a root-run
`systemctl --user` can never address the wrong user manager.

Both verifier secrets must then be entered locally through hidden terminal
prompts. They are never accepted as command arguments or environment values:

```bash
LD_LIBRARY_PATH=/absolute/owner-only/package/private/runtime-input \
PYTHONPATH=src /usr/bin/python3.13 -m overseer.activation_package \
  create-human-verifiers --package-root /absolute/owner-only/package
```

After local verifier creation, `finalize-package` seals all staged bytes and
returns the package digest. `verify-package --expected-digest DIGEST` checks
that digest and every recorded artifact. Live execution still requires a new,
explicit approval bound to that exact digest. The approved root operator then
uses `record-activation-approval` once; it writes a root-owned mode `0600`
record binding the package path and digest with scope
`sealed-package-import-and-verification-only`. This package record does not
authorize staging, canary, or cutover. Each execution phase requires its own
root-owned mode `0600` phase approval record.

Recording approval first copies every sealed package artifact to new inodes at
`/var/lib/overseer-executor/approved-package`, verifies the copied tree against
the approved digest, and binds the approval record and activation contract to
that root-owned mode `0700` execution copy. All installation and canary sources
come from this copy; the owner-writable preparation package is never consumed
by root after approval.

The approval import streams descriptor-bound files so the migration databases
are not constrained by the small control-document read limit. Sparse files and
packages above the fixed import-size bound are rejected, and the destination
filesystem must retain an equal-package-or-minimum operational headroom after
the copy. ENOSPC and other pre-publication failures remove only the private
temporary sibling. Every staged directory is synced bottom-up before the
verified tree is published with Linux atomic no-replace semantics. A parent
directory sync failure after publication is reported as durability-indeterminate
and leaves the unapproved destination for explicit recovery; it never creates
the approval record. Run the sealed entrypoint with bytecode writes disabled so
importing its modules cannot alter the finalized source package:

```bash
sudo env PYTHONDONTWRITEBYTECODE=1 \
  LD_LIBRARY_PATH=/absolute/package/public/release/RELEASE/lib \
  PYTHONPATH=/absolute/package/public/release/RELEASE/app/src:/absolute/package/public/release/RELEASE/site-packages \
  /usr/bin/python3.13 -B -s -P -m overseer.activation_package \
  record-activation-approval --package-root /absolute/package \
  --expected-package-digest DIGEST
```

If publication completed without an approval record, the same sealed
entrypoint provides `recover-activation-approval-import`. `--action adopt`
re-verifies both the finalized source and root-owned execution copy against the
same digest, syncs the privileged parent, and only then writes the approval.
`--action remove` verifies the finalized source/digest and removes only the
exact root-owned unapproved execution-package path before syncing its parent.
Both recovery actions refuse to run when an approval record already exists:

```bash
sudo env PYTHONDONTWRITEBYTECODE=1 \
  LD_LIBRARY_PATH=/absolute/package/public/release/RELEASE/lib \
  PYTHONPATH=/absolute/package/public/release/RELEASE/app/src:/absolute/package/public/release/RELEASE/site-packages \
  /usr/bin/python3.13 -B -s -P -m overseer.activation_package \
  recover-activation-approval-import \
  --source-package-root /absolute/package \
  --expected-package-digest DIGEST --action adopt
```

The sealed `activation-contract.json` is the authoritative command set. Do not
copy commands out of that contract or run them individually. Automatic
staging-to-cutover execution is forbidden: `execute-approved-activation`
fails closed. The supported entrypoints are
`execute-approved-staging-canary`, `execute-approved-cutover`, and
`execute-approved-rollback`. Each state-machine invocation records a command
digest before and after every step and holds one root-owned nonblocking
execution lock. Every mutating child inherits the same kernel lock descriptor,
so loss of the parent runner cannot release the lock while its child is still
running. The staging/canary runner requires a separate
`staging-canary` approval recorded while no runner state exists. On success it
stops the disposable approval-smoke fixture, the canary, and both staged
sockets and records
`canary_passed_awaiting_cutover_approval`; it cannot execute a cutover command.
The cutover approval can be recorded only after that state exists and binds its
exact canonical digest. `execute-approved-cutover` refuses any state or
approval drift before exposing the legacy-service stop.

After installing and verifying staged artifacts, but immediately before the
first canary socket or service start, the staging runner collects both canary
verifier secrets through hidden local prompts on one validated terminal
descriptor and validates them against the sealed package verifier documents.
Echo suppression is mandatory and there is no stdin fallback. The human wait is therefore outside the
canary unit's `RuntimeMaxSec` lifetime and the secrets are not retained during
package installation. After the prompts return, the runner re-verifies the
package, contract, active lock, unchanged runner state, exact canonical canary
startup suffix with no earlier canary start, exact canary command, and original
phase approval before starting any canary resource. It carries the
two values only in process memory and sends one bounded canonical packet to the
sealed `run-approved-canary` child over an anonymous stdin pipe. The packet is
never a command argument, environment value, log entry, file, or runner-state
field. Prompt or authority failure runs the sealed cleanup and records a
secret-free terminal state. The child proves the inherited lock, exact active
command state, executable, isolation flags, module, and package root before it
reads stdin; it then refuses interactive stdin, malformed framing, or trailing
data. It validates the values again against the installed verifier documents
before using either value. The canary's bounded lifetime still starts normally
when systemd starts the service, but no operator response is required inside
that window.

The public canary and final-store migration primitives independently require
the exact active phase, command index, sealed command digest, exact argument
map, and inherited execution-lock descriptor; stale state or a concurrent CLI
or Python caller cannot impersonate the runner. If a command succeeds or fails
but its next state, cleanup, or rollback checkpoint cannot be published, the
runner retries the complete idempotent sealed cleanup/rollback sequence without
depending on that checkpoint, then records a terminal recovery state when the
state filesystem is writable. A stale cutover checkpoint remains safely
resumable: exact rollback transients are reconciled instead of rejected.
This recovery boundary includes entry checkpoints for every later command and
process interruption while a command is running. Principal drift cannot
suppress sealed stop-only containment; recovery stops the successor and
restores numeric legacy ownership before refusing to start any named-principal
rollback transient whose identity no longer matches the contract.
Rollback contract normalization validates the sealed numeric authority schema
without consulting current NSS state; live name-to-ID checks occur only at
commands that actually start or consume a named principal. The execution-lock
path is revalidated against the locked descriptor after `flock` succeeds.

The first sealed staging command is an idempotent dedicated-principal
bootstrap implemented by the root-owned package release. It may run only as
the active staging command while inheriting the activation lock. It derives
the required user, group, numeric IDs, home, and shell from the sealed
contract; accepts only the exact existing identity; creates only a missing
group or user needed to complete that identity; and revalidates NSS state
after each tightly bounded `groupadd` or `useradd` invocation. The helper is
the only activation path permitted to invoke those account managers. A
mismatched name-to-ID binding, user without its required group, duplicate NSS
entry, membership in any foreign supplementary group, supplementary member,
foreign primary-group member, unlocked password, unexpected command failure,
or unsuccessful persistence aborts before any later staging action. All
installed ownership and systemd identities for the dedicated principal use the
sealed numeric UID/GID, preventing later name-resolution drift. Raw or wrapped
`groupadd` and `useradd` commands are forbidden anywhere else in the sealed
activation contract. The package-resident bootstrap and all root Python
primitives set `PYTHONDONTWRITEBYTECODE=1` and use `-B`, so verification cannot
be invalidated by import-time bytecode writes. These rules keep
replacement-package retries safe after a prior package created the account but
failed before cutover.

An interrupted staging run can execute its sealed socket/canary cleanup; an
interrupted cutover can execute `execute-approved-rollback`. Recovery accepts
the exact v1 approval/runner schemas only for rollback, never for new staging or
cutover, so an interrupted earlier activation remains recoverable after this
runner upgrade. Rollback binds the saved command index and digest to the sealed
command list. Its
digest-unique transient units are created only in the root-controlled system
manager with the sealed numeric UID/GID of the source-store owner; recovery
revalidates their root-owned unit file,
description marker, environment, executable, working directory, principal,
restart policy, ordering, credential presence, and active/sub states. It can
resume activating units, restart an exact inactive or failed unit, or recreate
an unloaded unit without accepting a same-name mismatch. No runner can start
from the package approval alone.

## Change boundary

The activation may create only:

- system user/group `overseer` with no login shell;
- root-owned release `/opt/overseer/releases/<commit>-<manifest-digest>`;
- protected state `/var/lib/overseer` and root executor state
  `/var/lib/overseer-executor`;
- configuration `/etc/overseer`;
- system units `overseer-api.service`, `overseer-runtime.service`,
  `overseer-admin-executor.socket`, `overseer-admin-executor@.service`, and the
  disposable `overseer-approval-smoke.service`;
- system socket/service `overseer-codex-user-bridge.socket` and
  `overseer-codex-user-bridge.service`, whose process runs as `god` but exposes
  only the two reviewed read-only methods;
- tmpfiles rule `/etc/tmpfiles.d/overseer.conf` creating `/run/overseer` with
  numeric owner/group `0:984` mode `0710`; each service socket has its own
  numeric owner and mode `0600`;
- one user-readable compatibility copy of the ordinary API client token at the
  existing path. This is not a human approval secret.

It may not change gateway, firewall, route, VPN, SSH, other-project source,
other-project services, Codex login files, tmux state, or any non-Overseer
database.

## Prepared artifacts

The final activation package must contain hashes for:

- every source file, dependency, standard-library file, and resolved Python
  interpreter copied into the immutable release;
- the approved private SQLite library, its exact SQLite version and source ID,
  required compile options, source-archive SHA3-256, and release-local path;
- all rendered units, the exact tmpfiles rule, and the exact root executor allowlist;
- the copied Psychlo binding snapshot;
- the live database's stable device/inode/owner/mode identity plus the rehearsal
  backup and migrated-canary hashes. The final quiesced backup and migrated
  authority hashes are activation evidence because the live database continues
  changing until the approved outage begins;
- both verifier documents, the executor public key, and credential metadata
  without secret values;
- the fresh ordinary API token metadata and the exact post-start compatibility
  copy target, without changing the live v1.1.5 token during preparation.

The final cutover does not treat point-in-time `/proc` descriptor and mapping
scans as its security boundary, and it never checkpoints the legacy source in
place after the service stop. After write-access revocation, the root migration
process acquires Linux read leases on the exact descriptor-bound database, WAL,
and shared-memory inodes. Lease acquisition fails if a writable open-file
description or mapping remains, including a file reference held only inside a
Unix-socket `SCM_RIGHTS` queue. Before any activation-owned metadata change,
every leased descriptor and pathname is revalidated against the complete
pre-open device, inode, type/mode, owner, link, size, modification-time, and
change-time identity. The exact database and WAL bytes are then copied through
those open descriptors, and the WAL is checkpointed only on that isolated
backup copy. The leases remain held through both source hashes and the complete
normalized backup; `SIGIO` lease-break requests and `F_GETLEASE` state are
checked throughout the operation. Missing lease support, a rejected lease, a
metadata mismatch, or a lease-break request fails the migration and removes its
partial outputs. The `/proc` checks remain as additional audit and
defense-in-depth evidence.

The v1.1.5 authority was written by the host SQLite runtime, while v1.1.6 uses
the sealed release-local runtime. Expression-index keys can legitimately need
recomputation across that runtime boundary even when the underlying table and
B-tree structure are sound. Both rehearsal and final migration therefore run a
pre-normalization `quick_check` on the copied store, require the exact reviewed
`idx_host_snapshots_captured_at` definition, rebuild only that copied expression
index, exit WAL mode on the copy, and then require the full `integrity_check`
and retained-row evidence. A structural quick-check failure, an altered index
definition, any unapproved reindex target, or a post-reindex integrity failure
still fails closed. The legacy source database and its index are never rebuilt
or otherwise mutated by package preparation or cutover.

Because the always-on scheduler continuously commits to the WAL, owner-scoped
package preparation uses Python/SQLite's documented `pages=-1` single-step
backup mode with no artificial sleep. Incremental backup steps restart after an
external commit; a single SQLite step instead retains one WAL reader snapshot
for the copy while normal writers continue, although checkpoint truncation may
wait for that reader. The preparation process itself must run at nice level 10
with idle-I/O scheduling, and live health is checked before and after the copy.
The source must report `journal_mode=wal`; otherwise preparation fails closed.
The exact single-step bound, WAL mode, and backup start/completion timestamps are
recorded in `migration-report.json`.

The package builder and all rendered v1.1.6 Python invocations use the sealed
SQLite 3.53.4 library at `lib/libsqlite3.so.0`. Its approved source ID is
`2026-07-24 19:02:57 bf7c7f30031888f4e796e429ab3978879485813aaca6f641c7b33e4e09459bcc`,
and the upstream source archive SHA3-256 is
`454e45f61c6bd75b7420e7190732dea03ce6639c63ada47bbc592f67fc340338`.
The independently reviewed compiled-binary SHA-256 is
`ca4c66d9a6b3d24b27e05f8d1cfd7ae620e5862df39c96164910885797d6fc2e`.
The deterministic `scripts/build_sqlite_runtime.sh` recipe verifies the source
archive, compiles with fixed GCC 14.2.0 flags and SQLite definitions, and
refuses any output that does not match that binary digest. Two clean builds
must compare byte-for-byte before the binary is admitted as a build input.

Package preparation refuses a different binary digest, version, source ID,
mapped device/inode, compile-feature set, owner, mode, link count, or build
provenance. The staging directory is owner-only mode `0500`. The runtime probe
keeps the approved file descriptor open, preloads `/proc/self/fd/<fd>` into the
isolated child, verifies the mapped device/inode, and rechecks the same inode and
digest after probing. The builder itself must be launched with
`LD_LIBRARY_PATH` pointing to the package's staged runtime directory and must
receive that exact path through `--sqlite-library`. This avoids changing the
host SQLite package or any other project while carrying the WAL-reset fix inside
the immutable Overseer release.

Finalization and every later package verification parse the rehearsal report
semantically. Sealing fails unless the report proves successful WAL-mode,
single-step `pages=-1`, zero-sleep backup, valid ordered timing evidence,
integrity success, no source mutation, and valid retained-row counts. Merely
placing a JSON file at the expected path is insufficient. Both rehearsal
database paths are derived from the package root, not trusted from JSON. The
verifier hashes each exact open inode, reruns `integrity_check`, schema
inventory, and retained-row counts through an immutable descriptor-backed
SQLite connection, and compares every observed hash, size, schema, count, and
integrity result with the report. Missing, replaced, linked, or concurrently
changed database bytes fail closed even if the package manifest was resealed.

Admin and Roadex approval secrets are entered interactively during verifier
creation, are confirmed once, and are never written, printed, logged, placed in
an environment variable, or reused. The documents contain only salts and
digests. The two secrets must be different from each other and from the API
token. Because independently salted verifier documents cannot be compared at
startup, both approval routes authenticate each submitted bearer against both
scopes and reject it with `approval_credential_scope_collision` if it verifies
for both.

Generate both staged verifier documents with
`python3 -m overseer.activation_package create-human-verifiers`. Each secret is
at least 20 UTF-8 bytes with no whitespace or control characters.
The former plaintext human-approval file is neither copied nor parsed by
v1.1.6; it remains only inside the preserved rollback boundary.

## Rendered activation commands

The package renders one argv array per operation. It contains no shell, glob,
recursive copy, secret argument, or unresolved value. Release installation
uses one `install` command per inventoried file and then freezes release
directories mode `0555`. Every system unit executes the release-local
`runtime/bin/python3.13` with release-local `PYTHONHOME`, source, dependency,
standard-library, and SQLite library paths.

The interpreter still uses the host's root-managed dynamic loader and shared
libraries as the operating-system trusted computing base. Direct and extension
dependencies include libc, libm, zlib, Expat, OpenSSL/libcrypto, and zstd. They
are not copied into the release; OS package integrity and the final activation
preflight remain responsible for them. SQLite is the explicit exception: the
approved private library is copied, hashed, installed `root:root` mode `0555`,
and selected with release-local `LD_LIBRARY_PATH` in system units, migration
commands, activation helpers, and sealed rollback transients. Every
release-local invocation uses `-s -P`, `PYTHONNOUSERSITE=1`, and
`PYTHONSAFEPATH=1`, so a user-writable site package, `sitecustomize.py`, or
working directory cannot enter the approved import path.

Before any canary request, `verify_installed_staging` hashes every installed
file against the approved package manifest and checks each destination's exact
owner, group, mode, type, and single-link identity. This closes the interval
between reading the owner package and consuming the root-installed artifacts.
Canary reads credentials only from the protected installed paths, not from the
owner-writable package. The post-start compatibility token is copied from
verified `/etc/overseer/api-token`, never from the owner package, and is
installed `root:god` mode `0640` below the retained non-writable legacy-state
parent. Its content, ownership, mode, and parent identity are reverified before
activation can complete.

The rendered API unit must set
`OVERSEER_PSYCHLO_PROJECT_BINDINGS_FILE=/etc/overseer/psychlo-project-bindings.json`.
The socket-activated executor applies a five-second default, at most
thirty-second, socket-I/O timeout; its unit also sets `RuntimeMaxSec=30s` and
`TimeoutStopSec=5s`. These are acceptance assertions, not tunable activation
placeholders.

The final primary database is copied only from a quiesced, WAL-consistent backup.
Historical approval and execution rows are retained for evidence but marked
non-executable by the migration. The final migration command is a reviewed
Overseer subcommand bound to the captured source and parent identities; it is not a
raw `cp` of a live SQLite file.

The rendered contract stops the old user units through `runuser` with the
captured `XDG_RUNTIME_DIR`, then invokes the immutable release's
`prepare-final-store` primitive. That primitive runs only as root and binds the
source database and parent directory device/inode/owner/mode. It temporarily
revokes the legacy account's traversal and write access, rejects open source
inodes and closed-descriptor shared mappings for the database, WAL, and SHM,
then revalidates the exact source inode after acquiring the parent lock. The
open-file/mapping checks repeat immediately before baseline hashing and after
the backup.
All subsequent source, WAL, and SHM access is anchored to the locked parent
directory descriptor. It checkpoints and truncates WAL, makes the source
artifacts read-only, hashes before and after the bounded SQLite backup, checks again for open
processes, and only then migrates a separate copy. It validates
integrity/schema/key-table counts and records the backup and migration evidence
below the root-owned executor state directory. On success the legacy-state
parent remains `root:god` mode `0555`, and the old database remains root-owned
read-only, until sealed rollback. A failure or rollback restores the exact
captured legacy ownership and parent mode.

## Staged start and acceptance

After artifact verification and separate approval of each rendered phase:

1. verify the sealed package against the separately approved digest and create
   the root-owned import/verification-only package approval record;
2. after a separate staging/canary approval, record
   `record-activation-phase-approval --phase staging-canary` and invoke only
   `execute-approved-staging-canary`. The operator enters both fresh verifier
   secrets through local hidden terminal prompts; secrets are never pasted
   into chat or passed through argv or environment variables;
3. create a new root-published, package-bound namespace below
   `/var/lib/overseer-canary/<canary-instance-id>/`, beneath a root-owned
   parent that the service principal cannot replace; fail closed if that
   namespace already exists; copy the rehearsed migrated authority database
   with no-replace semantics; pre-create pristine Psychlo and Roadex database
   files; and verify the exact hashes, ownership, modes, SQLite integrity and
   schema, and absence of WAL, SHM, journal, or other unexpected artifacts
   before any staged service starts. The package-specific namespace is
   preserved after success or failure as evidence and is never recycled by
   staging cleanup;
4. daemon-reload and start the user-bridge and executor sockets only;
5. start the non-enabled bounded `overseer-api-canary.service`. Systemd creates
   a private mode-`0700` runtime directory for the dedicated `overseer`
   principal, and that principal creates its own mode-`0600` Unix listener.
   Peer-secret readers accept private regular files owned only by the running
   principal or UID 0. Systemd may present a root-managed `LoadCredential=`
   file as mode `0440`; that mode is accepted only for a single-link,
   root-owned/root-group file opened relative to the descriptor for the active
   absolute `CREDENTIALS_DIRECTORY`. The reader opens every directory component
   with `O_NOFOLLOW`, requires root ownership with no group/world write access,
   and requires the final credential directory to be root-owned/root-group mode
   `0500` or ACL-mask-equivalent `0550`. Group-readable files outside that
   private systemd boundary, hardlinks, symlinks, and world-accessible
   credential files remain rejected, so persistent credential copies stay
   root-owned mode `0600`.
   The non-secret project-bindings document uses a separate descriptor-bound
   reader that permits root/service-owned read-only files such as mode `0644`
   but rejects multiple links and any group/world write bit. The Roadex relay
   uses its exact internal question endpoint, including
   `/api/internal/overseer/project-human-thread/questions`.
   A bounded health request retries all connection errors, including an
   initially absent socket pathname. The API accepts only root as the client
   and exposes no TCP listener;
6. run the digest-bound live canary controls through that Unix socket. Before
   sending an API token or approval secret, the client verifies the private
   socket path/owner/mode and the kernel-reported dedicated server UID. Then
   verify API health, bounded usage projection, read-only session projection,
   ordinary-token rejection, wrong-scope rejection, Sisko-scoped approval,
   exactly one allowlisted smoke restart, no-mutation replay, and unlisted-unit
   rejection. Write the exact root-owned attestation, then stop the disposable
   approval-smoke fixture, the canary, and both staged sockets. Systemd removes
   the canary runtime directory. Record
   `canary_passed_awaiting_cutover_approval` and return without touching the
   live v1.1.5 services;
7. after a later explicit cutover approval, record
   `record-activation-phase-approval --phase cutover`. This record binds the
   exact awaiting-cutover runner-state digest. Invoke only
   `execute-approved-cutover`;
8. run `verify-approved-cutover`; it re-verifies the package, installed
   artifacts, root approval record, exact canary control set, package digest,
   matching smoke/replay execution IDs, and exact `god`/`overseer` numeric
   identities before exposing the legacy stop;
9. quiesce the two old user units, take the final migration backup, bind the
   system API to `127.0.0.1:8766`, and start runtime/API;
10. rotate the ordinary API compatibility copy only after the new system API
   is started, so the running v1.1.5 API cannot be stranded with mismatched
   client credentials during canary preparation;
11. verify direct API health, protected-gateway health, UI desktop/tablet/mobile
   behavior, scheduler leases, and integration status;
12. keep all non-smoke executor operations disabled.

Package generation, human-verifier creation, finalization, and digest
verification do not authorize removing a previous root package approval,
importing the replacement package, recording either phase approval, or
executing either phase. Those remain separate exact approval gates.

The live control set above is mandatory and exact. Modified/expired tickets,
reused nonces, direct user-service commands, socket stalls, and
crash-after-claim behavior remain mandatory pre-activation regression tests;
they are not represented as live-canary booleans unless actually exercised.

## Rollback

Rollback is triggered by API/gateway failure, missing scheduler heartbeats,
database mismatch, integration regression, unauthorized acceptance, executor
replay, or any ownership/mode drift.

The package contains a private copy of every rollback input. Staging installs
those bytes into a root-owned, `god`-group-readable but non-writable,
digest-bound bundle below
`/opt/overseer/rollback`. The sealed rollback argv is the only approved form.
It first runs `verify-rollback-bundle`, then stops and disables only the new
system services,
restores the captured legacy database access through

Raw fragment validation also rejects inline or encrypted credential injection,
environment unsetting, temporary or image-backed filesystem mounts, bind
mounts, and privileged executable prefixes.
The ownership-restoration primitive also requires the inherited runner lock and
the exact active rollback command plus sealed arguments. Cleanup accepts only
the exact `systemctl is-active` inactive result for every listed unit; unknown
units, manager or bus failures, and other query errors fail closed.

Rollback restores the prior user units and their untouched original database;
it does not copy the migrated system database back over the old authority.
System-state, config, release, and executor artifacts remain inert and retained
for audited cleanup. Deleting the account, release, database, keys, or evidence
requires a separate exact cleanup approval.

- gateway and integration acceptance checklist;
