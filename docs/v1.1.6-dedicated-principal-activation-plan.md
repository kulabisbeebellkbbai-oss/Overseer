# Overseer v1.1.6 dedicated-principal activation plan

Approval status: architecture approved; live activation not approved.

Work type: high-risk local account, ownership, system-service, credential, and
authority-store migration.

Hardware requirement: none. An authenticated local administrator must be
present for the activation and rollback checkpoints.

## Preparation package implementation

The source implementation in `overseer.activation_package` prepares this plan
without executing it. `prepare-package` accepts only paths and numeric account
identifiers, creates an owner-only package, inventories the clean Git source,
release-local dependencies, the resolved interpreter, the complete standard
library, rendered units, credentials, and rollback inputs, and performs a
throttled online SQLite backup rehearsal. It migrates only a second copied canary and stops with status
`awaiting_human_verifiers`.

The package's `activation-contract.json` stores exact argv arrays and always
sets `liveExecutionApproved` to `false`. It is evidence for a later approval;
it is not an executable shell script and preparing or sealing it grants no
activation authority. The contract uses the exact `god` user-manager runtime
path when stopping or restoring the v1.1.5 user units, so a root-run
`systemctl --user` can never address the wrong user manager.

Both verifier secrets must then be entered locally through hidden terminal
prompts. They are never accepted as command arguments or environment values:

```bash
PYTHONPATH=src /usr/bin/python3.13 -m overseer.activation_package \
  create-human-verifiers --package-root /absolute/owner-only/package
```

After local verifier creation, `finalize-package` seals all staged bytes and
returns the package digest. `verify-package --expected-digest DIGEST` checks
that digest and every recorded artifact. Live execution still requires a new,
explicit approval bound to that exact digest. The approved root operator then
uses `record-activation-approval` once; it writes a root-owned mode `0600`
record binding the package path and digest. Canary and cutover commands refuse
to proceed without that record.

Recording approval first copies every sealed package artifact to new inodes at
`/var/lib/overseer-executor/approved-package`, verifies the copied tree against
the approved digest, and binds the approval record and activation contract to
that root-owned mode `0700` execution copy. All installation and canary sources
come from this copy; the owner-writable preparation package is never consumed
by root after approval.

The sealed `activation-contract.json` is the authoritative command set. Do not
copy commands out of that contract or run them individually. The only approved
entrypoint is `execute-approved-activation`; its root-owned state machine runs
the staged sequence, failure cleanup, cutover gate, cutover, and automatic
rollback in order. It records a command digest before and after every step,
holds one root-owned nonblocking execution lock for the complete operation,
checks every cleanup result, and records every automatic rollback step. An
interrupted staging run can execute its sealed socket/canary cleanup; an
interrupted cutover can execute `execute-approved-rollback`. Active transient
rollback units have digest-unique names and are verified instead of started a
second time. The runner cannot start without the user's root-owned
final-package approval record.

## Change boundary

The activation may create only:

- system user/group `overseer` with no login shell;
- root-owned release `/opt/overseer/releases/<commit>-<manifest-digest>`;
- protected state `/var/lib/overseer` and root executor state
  `/var/lib/overseer-executor`;
- configuration `/etc/overseer`;
- system units `overseer-api.service`, `overseer-runtime.service`,
  `overseer-admin-executor.socket`, `overseer-admin-executor@.service`, and the
  disposable `overseer-approval-smoke.service`;
- system socket/service `overseer-codex-user-bridge.socket` and
  `overseer-codex-user-bridge.service`, whose process runs as `god` but exposes
  only the two reviewed read-only methods;
- tmpfiles rule `/etc/tmpfiles.d/overseer.conf` creating `/run/overseer` as
  `root:overseer` mode `0750`;
- one user-readable compatibility copy of the ordinary API client token at the
  existing path. This is not a human approval secret.

It may not change gateway, firewall, route, VPN, SSH, other-project source,
other-project services, Codex login files, tmux state, or any non-Overseer
database.

Record these read-only results before any change:

```bash
id

getent group overseer || true

systemctl status overseer-api.service overseer-runtime.service overseer-admin-executor.socket --no-pager || true
systemctl status overseer-codex-user-bridge.socket overseer-codex-user-bridge.service --no-pager || true
curl --fail --silent --show-error http://127.0.0.1:8766/health
readlink -f /home/god/.local/share/overseer/project
test "$(grep '^OVERSEER_INSTALL=' /home/god/.config/overseer/runtime.env)" = \
  'OVERSEER_INSTALL=/home/god/.local/share/overseer/releases/v1.1.5-5196757'
test -d /home/god/.local/share/overseer/releases/v1.1.5-5196757
systemctl --user cat overseer.service overseer-api.service
stat -c '%d %i %a %U:%G %s %n' /home/god/.local/share/overseer/project/state/overseer.sqlite3
git -C '<reviewed-worktree>' status --porcelain=v1 --untracked-files=all
git -C '<reviewed-worktree>' rev-parse HEAD^{commit} HEAD^{tree}
```

Stop if the account already exists with different attributes, a system unit
name is already owned by another package, the live API is unhealthy, the
reviewed tree is dirty, the old database is not owner-only, WAL backup cannot
be obtained, the gateway owner has an unreviewed route change, or any required
user bridge remains incomplete. Also stop unless both rollback units are bound
to the preserved v1.1.5 release and their unit, drop-in, runtime-environment,
interpreter, and release-manifest hashes have been captured in the activation
package. The v1.1.6 checkout must never be substituted into those user units.

## Prepared artifacts

The final activation package must contain hashes for:

- every source file, dependency, standard-library file, and resolved Python
  interpreter copied into the immutable release;
- all rendered units, the exact tmpfiles rule, and the exact root executor allowlist;
- the copied Psychlo binding snapshot;
- the live database's stable device/inode/owner/mode identity plus the rehearsal
  backup and migrated-canary hashes. The final quiesced backup and migrated
  authority hashes are activation evidence because the live database continues
  changing until the approved outage begins;
- both verifier documents, the executor public key, and credential metadata
  without secret values;
- the fresh ordinary API token metadata and the exact post-start compatibility
  copy target, without changing the live v1.1.5 token during preparation.

Admin and Roadex approval secrets are entered interactively during verifier
creation, are confirmed once, and are never written, printed, logged, placed in
an environment variable, or reused. The documents contain only salts and
digests. The two secrets must be different from each other and from the API
token. Because independently salted verifier documents cannot be compared at
startup, both approval routes authenticate each submitted bearer against both
scopes and reject it with `approval_credential_scope_collision` if it verifies
for both.

Generate both staged verifier documents with
`python3 -m overseer.activation_package create-human-verifiers`. Each secret is
at least 20 UTF-8 bytes with no whitespace or control characters.
The former plaintext human-approval file is neither copied nor parsed by
v1.1.6; it remains only inside the preserved rollback boundary.

## Rendered activation commands

The package renders one argv array per operation. It contains no shell, glob,
recursive copy, secret argument, or unresolved value. Release installation
uses one `install` command per inventoried file and then freezes release
directories mode `0555`. Every system unit executes the release-local
`runtime/bin/python3.13` with release-local `PYTHONHOME`, source, dependency,
and standard-library paths.

The interpreter still uses the host's root-managed dynamic loader and shared
libraries as the operating-system trusted computing base. Direct and extension
dependencies include libc, libm, zlib, Expat, OpenSSL/libcrypto, libsqlite3,
and zstd. They are not copied into the release; OS package integrity and the
final activation preflight remain responsible for them. Every release-local
invocation uses `-s -P`, `PYTHONNOUSERSITE=1`, and `PYTHONSAFEPATH=1`, so a
user-writable site package, `sitecustomize.py`, or working directory cannot
enter the approved import path.

Before any canary request, `verify_installed_staging` hashes every installed
file against the approved package manifest and checks each destination's exact
owner, group, mode, type, and single-link identity. This closes the interval
between reading the owner package and consuming the root-installed artifacts.
Canary reads credentials only from the protected installed paths, not from the
owner-writable package. The post-start compatibility token is copied from
verified `/etc/overseer/api-token`, never from the owner package, and is
installed `root:god` mode `0640` below the retained non-writable legacy-state
parent. Its content, ownership, mode, and parent identity are reverified before
activation can complete.

The rendered API unit must set
`OVERSEER_PSYCHLO_PROJECT_BINDINGS_FILE=/etc/overseer/psychlo-project-bindings.json`.
The socket-activated executor applies a five-second default, at most
thirty-second, socket-I/O timeout; its unit also sets `RuntimeMaxSec=30s` and
`TimeoutStopSec=5s`. These are acceptance assertions, not tunable activation
placeholders.

The final primary database is copied only from a quiesced, WAL-consistent backup.
Historical approval and execution rows are retained for evidence but marked
non-executable by the migration. The final migration command is a reviewed
Overseer subcommand bound to the captured source and parent identities; it is not a
raw `cp` of a live SQLite file.

The rendered contract stops the old user units through `runuser` with the
captured `XDG_RUNTIME_DIR`, then invokes the immutable release's
`prepare-final-store` primitive. That primitive runs only as root and binds the
source database and parent directory device/inode/owner/mode. It temporarily
revokes the legacy account's traversal and write access, rejects open source
inodes, checkpoints and truncates WAL, makes the source artifacts read-only,
hashes before and after the bounded SQLite backup, checks again for open
processes, and only then migrates a separate copy. It validates
integrity/schema/key-table counts and records the backup and migration evidence
below the root-owned executor state directory. On success the legacy-state
parent remains `root:god` mode `0555`, and the old database remains root-owned
read-only, until sealed rollback. A failure or rollback restores the exact
captured legacy ownership and parent mode.

## Staged start and acceptance

After artifact verification and a separate approval of the rendered plan:

1. verify the sealed package against the separately approved digest, create
   the one-use root-owned activation approval record, and invoke only
   `execute-approved-activation`;
2. daemon-reload and start the user-bridge and executor sockets only;
3. install the rehearsed migrated copy as
   `/var/lib/overseer/overseer-canary.sqlite3` and verify every installed
   artifact against the approved package before any staged service starts;
4. start the user bridge, executor socket, and non-enabled bounded
   `overseer-api-canary.service` on `127.0.0.1:18766`; verify initial health and
   bounded session and usage projections without modifying either user source;
5. run the digest-bound live canary controls: direct API health, bounded usage
   projection, read-only session projection, ordinary-token rejection,
   wrong-scope rejection, Sisko-scoped approval, exactly one allowlisted smoke
   restart, no-mutation replay, and unlisted-unit rejection. Write the exact
   root-owned attestation, then stop the canary;
6. run `verify-approved-cutover`; it re-verifies the package, installed
   artifacts, root approval record, exact canary control set, package digest,
   matching smoke/replay execution IDs, and exact `god`/`overseer` numeric
   identities before exposing the legacy stop;
7. quiesce the two old user units, take the final migration backup, bind the
   system API to `127.0.0.1:8766`, and start runtime/API;
8. rotate the ordinary API compatibility copy only after the new system API is
   started, so the running v1.1.5 API cannot be stranded with mismatched client
   credentials during canary preparation;
9. verify direct API health, protected-gateway health, UI desktop/tablet/mobile
   behavior, scheduler leases, and integration status;
10. keep all non-smoke executor operations disabled.

The live control set above is mandatory and exact. Modified/expired tickets,
reused nonces, direct user-service commands, socket stalls, and
crash-after-claim behavior remain mandatory pre-activation regression tests;
they are not represented as live-canary booleans unless actually exercised.

## Rollback

Rollback is triggered by API/gateway failure, missing scheduler heartbeats,
database mismatch, integration regression, unauthorized acceptance, executor
replay, or any ownership/mode drift.

The package contains a private copy of every rollback input. Staging installs
those bytes into a root-owned, `god`-group-readable but non-writable,
digest-bound bundle below
`/opt/overseer/rollback`. The sealed rollback argv is the only approved form.
It first runs `verify-rollback-bundle`, then stops and disables only the new
system services,
restores the captured legacy database access through
`restore-legacy-store-access`, and addresses the `god` user manager through its
captured runtime directory. It starts transient rollback runtime/API units
using only the bundled v1.1.5 source plus the immutable release runtime, then
checks loopback health. It never executes the mutable retained user release or
unit files. Restoration re-checks the legacy database and parent directory
identities before changing ownership or mode.

Rollback restores the prior user units and their untouched original database;
it does not copy the migrated system database back over the old authority.
System-state, config, release, and executor artifacts remain inert and retained
for audited cleanup. Deleting the account, release, database, keys, or evidence
requires a separate exact cleanup approval.
