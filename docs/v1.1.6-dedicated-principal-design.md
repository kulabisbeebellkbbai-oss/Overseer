# Overseer v1.1.6 dedicated-principal design

Status: approved source design; not activated. This document authorizes no
account, permission, database, service, gateway, firewall, or external-project
change.

## Outcome

Overseer v1.1.6 separates three trust planes:

1. `god` remains an untrusted local client and owns Codex, tmux, browser, and
   user-native collectors.
2. the non-login system account `overseer` runs the API and autonomous runtime
   from a root-owned immutable release and exclusively owns the authoritative
   SQLite state;
3. a root-owned, socket-activated executor accepts only signed, short-lived
   tickets from `overseer`, rebuilds its own fixed command, and initially
   permits only the disposable approval-smoke system service.

The protected gateway keeps the existing loopback API listener. Other projects
are not edited. Integrations that require `god`'s session remain user-owned and
must cross a narrow bridge rather than opening Overseer's database.

## Incomplete-work disposition

### Integrate

- autonomous collection scheduling, request coalescing, bounded concurrency,
  retained projections, incident triage, and repair verification;
- the current operator UI and protected-gateway route;
- immutable-release validation already developed for the Codex dispatch work;
- crash-safe admin claims and immutable plan digests;
- scoped verifier documents and signed executor tickets added for v1.1.6;
- existing Roadex and Psychlo loopback protocols without modifying those
  projects.

### Keep inert until its bridge exists

- Codex/tmux dispatch and user-session inspection;
- Documents/Obsidian actions;
- user-specific Psychlo meter operations that need Codex authentication;
- any direct collector that depends on `god`'s user bus, private home files, or
  supplementary groups.

These surfaces remain visible as unavailable/disabled projections. They must
not silently fall back to broad home-directory mounts, shared database access,
or copied login credentials.

### Retire or abandon for v1.1.6

- plaintext human approval token files and client-selected approval identity;
- direct CLI approval and autonomous Sisko self-approval;
- user-owned API/runtime activation as a claimed security boundary;
- direct `systemctl --user` execution and arbitrary service targets;
- automatic retry after an execution claim with no terminal receipt;
- deferred historical branches already listed in
  `v1.1-incomplete-work-disposition.md`; they remain preserved but are not
  activation dependencies.

## Remaining activation blockers

- render and accept the implemented four-method read-only `god` user bridge,
  including peer UIDs, fixed source metadata, stale/error behavior, response
  bounds, and runtime-directory ownership;
- install the reviewed API-only project and Quark hooks and prove they fail
  closed without authority access;
- accept the implemented root executor after final signed-ticket, peer-UID,
  allowlist, durable-nonce-ledger, and crash-reconciliation review;
- render a release-specific immutable install manifest and hashes;
- perform a disposable copied-store migration rehearsal, including WAL/SHM,
  schema, owner, rollback, and old-approval invalidation checks;
- complete Chromium desktop/tablet/mobile acceptance through the real protected
  gateway after the system API is staged;
- pass final defensive security review before presenting the activation plan
  for execution approval.

## Non-negotiable boundaries

- No other project's source, service, database, or credential is modified by
  this design.
- Registration, health, a staged plan, or an acknowledged crew message never
  implies approval or activation.
- Historical approvals, claims, and completed executions are imported as
  non-executable evidence. Every v1.1.6 privileged action needs a fresh scoped
  approval and successor ticket.
- The normal user cannot write the active release, authority database,
  verifier documents, signing private key, executor code, executor allowlist,
  or executor ledger.
- The executor accepts no argv, environment, path, shell text, package name,
  firewall rule, or unit outside its root-owned allowlist.
