# Overseer v1.1.6 maintenance-window deployment

Approval status: design and package-preparation implementation approved. Package
import and maintenance-window execution are not approved.

Work type: bounded high-risk local service, privilege, credential, and SQLite
authority migration.

Hardware requirement: none. A local administrator must remain available for
the complete maintenance and rollback interval. SSH is acceptable when the
session has a stable interactive terminal; the runner includes an authenticated
Protected Gateway challenge that must be copied back into that terminal.

Implementation status: source implementation and focused verification are in
progress. Package finalization, the full repository suite, independent final
security review, and the unimported package digest remain pending.

## Why this replaces Phase B

The disposable-VM rehearsal and staged-canary path proved useful controls but
introduced multiple independent state machines: package import, Phase B
approval, VM ownership, canary lifecycle, claim continuation, cutover, and
cleanup. The replacement uses one maintenance approval and one execution lock
for a single host-local outage. It does not consume or reconcile an existing
Phase B, claim, VM, canary, or cutover record.

The high-assurance controls that remain mandatory are immutable release bytes,
root-owned package import, package and plan digest binding, exact argv sealing,
a dedicated unprivileged principal, offline-only
database conversion, single-writer enforcement, checkpointed execution,
acceptance evidence, and presealed automatic rollback.

The legacy Phase B, canary, and cutover commands remain present as a separate
activation path; this maintenance runner does not erase or silently repurpose
them. Human verifier secrets apply to the earlier package-finalization gate and
are not requested or stored by maintenance execution.

## Approval model

Package import remains its own exact digest approval. Import copies the sealed
owner package to the root-owned execution location and writes the required
root-owned activation approval record; it grants no maintenance execution
authority.

Maintenance execution then requires one distinct root-owned mode `0600`
document with schema `overseer.maintenance-window-approval.v1`. It binds:

- the root-owned execution package path and final package digest;
- the sealed maintenance contract and maintenance-plan digest;
- scope `maintenance-window-for-this-package-only`;
- an exact `allowReboot=false` policy for this package.

The maintenance-approval recorder refuses to operate after any maintenance
runner state exists. The approval document itself binds the package and plan,
not a separately serialized runner-state digest.

The approval cannot authorize package import, Phase B, VM lifecycle, claim
changes, gateway changes, manual command extraction, or a later package digest.
Rollback after writers have stopped is part of this one bounded approval so a
failure cannot wait for a second human decision while Overseer is offline.

## Sealed maintenance sequence

The root runner holds the existing nonblocking activation lock for the complete
window. Every child receives the same inherited descriptor. Commands are
executed directly as argv arrays with a fixed environment; no shell, glob,
command substitution, or copied command from a JSON document is supported.

1. Reverify the imported package, its activation approval, the distinct
   maintenance approval, the sealed plan digest, and the no-reboot policy.
2. Before outage, verify all four source-store identities, every preservation
   input, the complete writer-unit baseline, evidence-path ownership, total
   evidence size, and free-space headroom. Any failure exits without stopping a
   writer.
3. Stop every loaded Overseer user writer: runtime/API, Psychlo usage and
   coordination jobs, Quark scheduler jobs, and Codex Usage MCP/snapshot jobs.
   Psychlo, Roadex, and Protected Gateway services owned by other projects are
   not changed.
4. Prove the main database and its WAL/SHM files, the Psychlo bridge database,
   the Roadex relay database, and the deferred Codex Usage store have no open
   or mapped writer artifacts. The three stores being migrated also use the
   kernel lease barrier while each offline copy is made.
5. Preserve
   descriptor-bound raw database/WAL/SHM artifacts, the current immutable
   release, credentials, all relevant Overseer user-unit bytes, runtime
   environment, and existing rollback artifacts in a root-owned evidence
   directory. Sync files and directories before continuing.
6. Install and verify the new immutable release, credentials, units, tmpfiles
   rule, executor allowlist, and rollback bundle from the root-owned package.
7. Create consistent offline backups and migrate only new copies of the main,
   Psychlo, and Roadex databases. Run quick/integrity checks, schema ledgers,
   retained-row comparisons, and destination ownership checks. The legacy
   database contents remain unchanged; their access metadata is intentionally
   locked to root-owned read-only rollback authority after each successful
   copy.
8. Complete the dedicated-principal conversion on those offline copies by
   setting the sealed numeric owner/group only after validation. If any source
   cannot be converted safely, roll back instead of mixing old and new
   authorities. Dedicated-principal conversion of the independent Codex Usage
   store is explicitly deferred; it is preserved and resumed unchanged.
9. Re-hash the complete preservation namespace, disable the superseded user
   units, prove quiescence a second time, reload systemd, create runtime
   directories, and start the successor sockets/runtime/API in an ordered
   fail-closed handoff. This is not a cross-manager atomic systemd transaction;
   source-store authority locking and the second quiescence proof are the
   atomicity boundary.
10. Resume the unchanged Quark and Codex Usage integrations, then run bounded
   acceptance: direct API health, authenticated UI data, exact core collection
   freshness limits, an authenticated Protected Gateway challenge without
   gateway mutation, Psychlo and Roadex reads, credential metadata/API use, and
   expected successor/legacy writer-unit inventory.
11. On complete acceptance, persist a plan-bound acceptance report and terminal
    runner state, and leave the rollback
    bundle and raw snapshot untouched. On any failure after writer stop,
    immediately execute the sealed rollback sequence.

## Reboot policy

This replacement package supports `allowReboot=false` only and contains no
reboot command or post-boot continuation. Adding one approved reboot would
require a new reviewed implementation, replacement package digest, and
separate approval; it cannot be inferred from this maintenance approval.

## Acceptance and rollback

Acceptance is a read-only observation phase. It must not trigger broad probe
runs or collection requests. The API and UI read already-running Overseer data;
the scheduler is checked through bounded freshness records rather than by
forcing every collector at once.

The gateway control first validates the existing TLS login surface. The runner
then publishes a short-lived random challenge in the authenticated
`/Overseer/operator-dashboard` response and asks the operator to copy it back
from an existing gateway session. The acceptance stage has a sealed 900-second
(15-minute) timeout. The challenge is deleted whether it succeeds or fails; no
gateway configuration or session data is changed.

Rollback is mandatory after any post-stop failure. It stops and disables the
successor system services, verifies the immutable rollback bundle, restores
the legacy access metadata captured for all three migrated authorities,
re-enables the exact preflight-active legacy runtime/API/Psychlo and unchanged
Quark/Codex Usage units, and checks direct health. The current
release, unit bytes, credentials, runtime environment, raw stores, and package
rollback bundle were already copied into root-owned evidence before install.
Failed migrated copies and evidence are preserved for triage. Rollback never
copies a partially migrated database over the legacy authority and never
changes another project's service or gateway.

Rollback has a dependency barrier: all successor-stop and recovery-preparation
commands are attempted, but no legacy writer is started if rollback-bundle
verification or any store restoration fails. A rollback failure records a
terminal `rollback_failed` state and does not improvise repair commands.

## Outage expectations and hard bounds

Preflight runs before writer shutdown. Once writers stop, API/UI and scheduled
Overseer collection are unavailable until successor acceptance or rollback.
The sealed runner deadline is 5,400 seconds (90 minutes); rollback receives a
separate 1,800-second (30-minute) deadline. The maximum planned runner plus
rollback envelope is therefore 7,200 seconds (120 minutes).

The most recent available canary snapshot in the prior run was 1,510,240,256
bytes, approximately 1.407 GiB. Three full-size copies at that historical size
would be approximately 4.220 GiB before WAL/SHM, release, credential, unit, and
headroom costs. That snapshot may be stale, so preflight recomputes exact bytes
and free space. No narrower outage estimate should be promised until the final
sealed package is benchmarked against the current stores; reserve the complete
two-hour envelope.

## Stop conditions

Stop before writer shutdown on any package, import approval, maintenance
approval, contract, or plan-digest mismatch. Stop after writer shutdown and
roll back on any source identity, release, credential, unit, rollback artifact,
quiescence, preservation, fsync,
installation, migration, ownership, handoff, acceptance, or durable-checkpoint
failure.

Also stop on any command inventory containing Phase B/canary runners, VM tools,
claim operations, gateway/firewall tools, a shell interpreter, manual database
replacement, an executable/action/target outside the maintenance allowlist, or
a service outside the explicit Overseer-owned unit set. `systemctl reboot` and
other systemctl power verbs are rejected independently of executable-name
checks.

## Approval-rule changes required

- Add the maintenance approval schema and exact package/plan/no-reboot bindings.
- Require the existing root-owned activation/package-import approval as a
  prerequisite, while explicitly withholding Phase B and cutover authority.
- Permit a single approval to cover the ordered outage and automatic rollback;
  do not require a new approval while services are already stopped.
- Permit offline migration of the three explicitly bound Overseer data stores
  and numeric ownership conversion of new copies.
- Permit stopping the complete Overseer writer set and performing the ordered
  user-to-system handoff under the existing activation lock.
- Remove Phase B, VM, claim, canary, and cutover-state prerequisites from this
  runner only. Keep those rules intact for the legacy runners.
- Extend the executor/contract allowlist only for the sealed maintenance
  primitives, exact systemctl actions/units, bounded curl target, install
  targets, per-command timeouts, and global execution/rollback deadlines.
- Permit root to lock the three migrated legacy store authorities read-only,
  while expressly deferring authority conversion of the Codex Usage store.
- Keep package import, any future reboot support, gateway changes, and any other-project
  mutation as separate approvals.
- Permit the existing gateway route to expose the short-lived read-only
  acceptance field; no gateway rule or service change is authorized.

## Required approval sequence

1. The current approval authorizes source implementation, tests, reviews, and
   preparation of an owner-scoped package only.
2. After finalization, a new approval must name the final package digest and
   authorize `record-activation-approval` package import only. It must not
   authorize maintenance execution.
3. After imported-package verification, a separate approval must name the same
   package digest and the reported maintenance-plan digest and authorize
   `record-maintenance-window-approval` only.
4. A final explicit execution approval must authorize
   `execute-approved-maintenance-window` for those exact digests. It includes
   automatic rollback after writer shutdown, but no reboot, Phase B, cutover,
   VM, claim, gateway, firewall, or other-project authority.
5. No additional approval is required for automatic rollback. Any manual
   recovery after `rollback_failed` requires a new exact plan.

The finalized handoff will provide single-line launchers bound to the actual
release directory and digest so shell wrapping cannot alter an invocation.

## Alternative comparison

| Option | Strength | Main cost/risk | Approval impact | Recommendation |
| --- | --- | --- | --- | --- |
| Existing high-assurance cutover | Disposable rehearsal and strongest environmental separation | Multiple VM, claim, canary, package, and cutover state machines have made recovery and proof reconciliation fragile | Retains all existing phase approvals | Keep available, but do not use for this recovery |
| Bounded maintenance window | One host-local authority path, offline migration, direct evidence, and deterministic rollback | Planned API/UI/scheduler outage; operator must remain present | Requires the maintenance rules and three post-build approvals above | Preferred |
| Blue-green gateway | Can reduce visible API outage | Dual-writer/data synchronization risk and a Protected Gateway route change | Requires a separately reviewed gateway/security approval and other-project coordination | Propose only if the outage becomes unacceptable |

The blue-green option is not part of this package and cannot be inferred from
maintenance approval.

## Non-execution boundary

Preparing and sealing this package does not authorize import or execution. The
next approval after successful review must identify the exact final package
digest and authorize package import only. Maintenance approval and execution
remain a later, separate explicit decision.
